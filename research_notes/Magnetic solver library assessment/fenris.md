# Fenris magnetic solver library assessment

## Does Fenris implement the electromagnetic physics we need?

### Takeaway
No verified electromagnetic solver is supplied. Fenris is a low-level FEM assembly library with implemented nodal elements and solid-mechanics operators, not an implemented nonlinear magnetostatic or eddy-current application. Recommendation: neither production dependency nor validation-only solver for this project.

### Cited Findings
- The README explicitly targets low-level FEM functionality rather than a high-level PDE formulation system, emphasizes solid mechanics, and says the library itself is for assembling and applying discrete operators. This is not a magnetic solver product claim. [README](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/README.md)
- The implemented core operator module exports Laplace; `LaplaceOperator` has scalar solution dimension, no material parameters, and returns the supplied gradient. It does not implement nonlinear reluctivity or a B-H curve. The general `EllipticOperator` and `EllipticContraction` interfaces accept material parameters and gradient-dependent operators, so they are extension points, not implemented magnetic materials. [Operator interfaces](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/src/assembly/operators.rs#L5-L87), [Laplace implementation](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/src/assembly/operators/laplace.rs#L13-L50)
- The supplied nonlinear material implementations are `NeoHookeanMaterial` and `StVKMaterial`, alongside linear elasticity. These are mechanical constitutive laws, not magnetic saturation. [Materials source](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/fenris-solid/src/materials.rs)
- Core elliptic assembly requires `T: Real`, and `Real` is defined as `nalgebra::RealField + Copy`. Consequently these implemented assembly paths do not directly accept complex harmonic field scalars. A few generic interfaces using `Scalar` do not establish end-to-end complex PDE support. [Elliptic assembly](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/src/assembly/local/elliptic.rs#L361-L382), [Real trait](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/fenris-traits/src/lib.rs)
- In the reviewed repository tree, operator source, material source and examples, I found no implemented magnetostatics, B-H interpolation, permanent-magnet source model, harmonic eddy-current formulation, moving-conductor or moving-magnet formulation, magnetic force/drag postprocessor, or electromagnetic benchmark. This is a bounded source-review finding, not a claim that no downstream private implementation exists. [Repository tree](https://github.com/InteractiveComputerGraphics/fenris/tree/7181b15684ad1eb90d95cc75f1566a8259a0241d), [Core operators](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/src/assembly/operators.rs), [Example](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/examples/poisson2d.rs)

### Inferences
- A custom 2D scalar magnetic-potential application might reuse the real-valued nodal assembly machinery. It would still require our own magnetic weak form, B-H law and derivative, magnet sources, nonlinear convergence policy, boundary treatment, and force extraction. This would be a new solver development project, not integration of existing physics. This inference follows from the operator extension interfaces cited above.
- A real block representation of complex unknowns is mathematically possible, but no supplied harmonic magnetic application establishes its correctness or practical solver support. Do not count this as implemented complex eddy-current capability.
- The supplied problem context says attraction is 14–52% high for thick plates near the B-H knee, layered harmonic eddy currents already agree about 2% in 2D, and finite 5 mm magnet-depth 3D drag remains unverified. Fenris offers no ready implementation that closes either remaining validation gap. Generic FEM infrastructure would force us to validate a new solver before using it to validate our analytical model.

### Gaps
- No verified public magnetic validation cases or downstream magnetic application were located in the reviewed primary sources. No electromagnetic accuracy, force error, drag accuracy, or magnetic runtime claim can be made.
- The analytical error figures above come from the task assignment, not an independently reviewed benchmark source.

## What elements, meshing and solvers actually exist?

### Takeaway
Useful implemented FEM machinery exists in both 2D and 3D, but 3D geometric support is not evidence of a 3D electromagnetic formulation. Mesh import and limited procedural generation exist; solver utilities are more substantial than the README's old non-goal wording implies.

### Cited Findings
- Implemented 2D nodal elements include Tri3, Tri6, Quad4 and Quad9. There is also a Tri3 surface element embedded in 3D. [Triangle implementations](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/src/element/triangle.rs), [Quadrilateral implementations](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/src/element/quadrilateral.rs)
- Implemented 3D volume elements include Tet4, Tet10, Tet20, Hex8, Hex20 and Hex27. Tet10 documentation explicitly assumes an affine reference-to-physical transformation. [Tetrahedra](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/src/element/tetrahedron.rs), [Hexahedra](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/src/element/hexahedron.rs)
- Element interfaces expose nodal basis values and gradients; the reviewed element modules contain no Nedelec/H(curl) edge-element implementation or ready Maxwell curl-curl formulation. Vector-valued nodal unknowns are not evidence of H(curl)-conforming support. [Element interfaces](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/src/element.rs#L27-L50), [Finite-element space interfaces](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/src/space/mod.rs#L20-L62)
- Gmsh MSH 4.1 loading exists. It builds a mesh of vertices and connectivity for a requested supported element type. The loader does not return magnetic region/material or boundary-condition objects; application-side region mapping needs attention. [MSH loader](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/src/io/msh.rs#L1-L105)
- Procedural mesh routines generate uniform rectangular quad/tri meshes and box hex/tet meshes, and include basic 2D SDF approximation/voxelization. This is not a verified general CAD-to-conforming-volume-mesh workflow. VTK output is demonstrated by the Poisson example. [Procedural meshing](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/src/mesh/procedural.rs), [VTU example](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/examples/poisson2d.rs#L17-L28)
- Important README/source discrepancy: the README says Fenris provides no linear/nonlinear system solving, but the workspace includes real-valued preconditioned conjugate gradient in `fenris-sparse` and Newton with optional backtracking in `fenris-optimize`. Newton delegates Jacobian solves to a caller implementation. These utilities do not supply magnetic modeling. [README non-goals](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/README.md), [CG](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/fenris-sparse/src/cg.rs), [Newton](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/fenris-optimize/src/newton.rs#L54-L87), [Jacobian solver interface](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/fenris-optimize/src/calculus.rs#L30-L41)
- The example assembles CSR then converts to a dense matrix for Cholesky with `TODO: Use sparse solver`. It is a small Poisson example, not a demonstrated scalable electromagnetic solve. [Example solver](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/examples/poisson2d.rs#L88-L96)

### Inferences
- A standard 3D eddy-current A/phi implementation would need formulation and gauge choices, material interfaces, appropriate finite-element spaces, complex or real-block assembly, and a suitable linear solver/preconditioner. None is delivered as an electromagnetic workflow by the reviewed code. Existing CG should not be assumed appropriate for a complex indefinite or nonsymmetric system.
- Finite 5 mm magnet-depth drag validation is therefore not unlocked merely by the existing Tet/Hex element inventory.

### Gaps
- No verified adaptive skin-depth meshing, magnetic open-boundary treatment, moving mesh/sliding interface, EM-specific gauge handling, or force-integration validation was located.
- No measured memory/runtime scaling for a relevant 3D motor/backplane mesh was found. No build or simulation was run for this assessment.

## What are the maintenance, licensing and integration costs, and should we adopt it?

### Takeaway
Rust integration is mechanically simpler than embedding a separate native FEM application, but the dominant cost is writing and maintaining missing electromagnetic software. The public code and package have had no observed update since September 2023, and the current source explicitly discourages production use.

### Cited Findings
- `src/lib.rs` warns that the API is completely unstable, functionality insufficiently tested, documentation sparse, and production usage strongly discouraged. The README says only minor fixes are accepted while larger rework is planned. The README's status text dates itself to October 2021, so use current repository/package metadata rather than its roadmap as evidence of current activity. [Library warning](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/src/lib.rs#L1-L7), [README status and contributions](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/README.md)
- As checked on 2026-10-18, GitHub reports the repository is not archived, `pushed_at` is 2023-09-25, and latest master commit is `7181b15684ad1eb90d95cc75f1566a8259a0241d`, dated 2023-09-25, message `fenris-solid v0.0.33`. Do not confuse its 2026 GitHub `updated_at` timestamp with code maintenance. [Repository API](https://api.github.com/repos/InteractiveComputerGraphics/fenris), [Latest commits API](https://api.github.com/repos/InteractiveComputerGraphics/fenris/commits?per_page=5), [Pinned latest commit](https://github.com/InteractiveComputerGraphics/fenris/commit/7181b15684ad1eb90d95cc75f1566a8259a0241d)
- Crates.io reports latest and maximum `fenris` version `0.0.33`, published 2023-09-25, not yanked, with no declared `rust_version`. The GitHub releases endpoint returned an empty list. Crate publications therefore exist despite no GitHub releases. [Crate API](https://crates.io/api/v1/crates/fenris), [GitHub releases API](https://api.github.com/repos/InteractiveComputerGraphics/fenris/releases?per_page=3)
- The package uses Rust edition 2021, `nalgebra 0.32.1`, `nalgebra-sparse 0.9.0`, Rayon, VTK/MSH I/O, and several Fenris workspace crates. Default features are empty, but geometry is explicitly requested with its `proptest` feature and serde is mandatory. The root manifest lists no native external FEM engine, BLAS, PETSc or licensed solver requirement. This is a manifest observation, not a complete transitive-dependency portability audit. [Cargo manifest](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/Cargo.toml)
- Quadrature has a Rust build script generating rules from bundled data using Rust parsing/code-generation crates, rather than requiring an installed mesh generator or external numerical executable for that build step. [Build script](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/fenris-quadrature/build.rs#L1-L23), [Quadrature manifest](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/fenris-quadrature/Cargo.toml)
- The workspace declares `MIT OR Apache-2.0`, matching the README. Both license texts are included. This permits a permissive licensing choice for Fenris itself, subject to its terms and a separate dependency/license audit. [Manifest](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/Cargo.toml), [MIT](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/LICENSE-MIT), [Apache](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/LICENSE-APACHE)
- CI specifies stable Rust on Ubuntu with formatting, checks, docs, unit/integration tests, benchmarks-as-tests, and separate convergence tests. Existing convergence assets cover 2D/3D Poisson, not electromagnetic force or drag. This verifies test infrastructure exists, not that it passes today. [CI configuration](https://github.com/InteractiveComputerGraphics/fenris/blob/7181b15684ad1eb90d95cc75f1566a8259a0241d/.github/workflows/build.yml), [Convergence tests](https://github.com/InteractiveComputerGraphics/fenris/tree/7181b15684ad1eb90d95cc75f1566a8259a0241d/tests/convergence_tests)

### Inferences
- Production: reject for this task. Native Rust and permissive licenses do not offset missing EM physics, explicitly unstable APIs, and an observed three-year public code/publication gap.
- Validation-only: also reject as an off-the-shelf reference. Developing our own unvalidated magnetic code atop Fenris would not provide the independent established reference needed for near-knee saturation and finite-depth 3D drag. Reconsider only if the project intentionally funds a separate FEM solver R&D effort.
- Distribution: a Cargo-linked solver may avoid shipping a separate solver executable, but we would own magnetic material datasets, meshing/region assignment, solver/preconditioner choices and benchmark fixtures. External Gmsh use would require its own deployment and license decision; reading `.msh` files alone does not require embedding Gmsh.
- Suggested decision for the parent assessment: classify Fenris as a general FEM implementation toolkit, not a candidate magnetic solver. Keep the analytical model for production and use a separately verified EM solver for the two unresolved validation problems.

### Gaps
- No dependencies were installed, code built, target platforms tested, or project code inspected. Actual compile time, binary size, MSRV, Windows/macOS/WASM compatibility, and nalgebra-version interoperability remain unmeasured.
- Full transitive license/security review and external mesher distribution terms were outside this source-only assessment. Public inactivity does not prove maintainers have stopped all private work.
