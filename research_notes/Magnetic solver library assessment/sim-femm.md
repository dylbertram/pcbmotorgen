# sim-femm assessment

## What is it, and how does it compare with our FEMM workflow?

### Takeaway
sim-femm is an independent Rust finite-element library stack for the SIM runtime, not a wrapper, embedded copy, or automation layer for David Meeker's FEMM. Its public description overstates the physical capabilities of the inspected implementation. Do not replace the existing FEMM reference workflow with it.

### Cited Findings
- Assessment date is 2026-10-18. Inspected GitHub main at `dcc1205664cb74fc77aab7d62ae650cd2c0ac759`, dated 2026-09-29. All implementation conclusions below concern that revision, not an executed build or an assumed future release. [Commit](https://github.com/sim-nest/sim-femm/commit/dcc1205664cb74fc77aab7d62ae650cd2c0ac759)
- The project explicitly describes loadable Rust libraries, not a standalone binary. It supplies geometry, meshing, assembly, solve, postprocessing, sensitivity, and ODE adapters on `sim-kernel` and `sim-numbers`. The documented Rust entry point installs `FemmPreludeLib` into a SIM `Cx`. The optional `sim` CLI belongs to the wider ecosystem. [README](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/README.md)
- This identity is verified in code, not inferred from the name. `solve_steady` calls its own `DeterministicMesher`, Rust `assemble_system`, and linear solver or PTC code. Assembly computes local residuals and AD derivatives, assembles a matrix, and applies boundary conditions. This is an in-process solver implementation, not a FEMM subprocess call. [Solve](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-solve/src/steady.rs#L52-L126), [assembly](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-assembly/src/implementation.rs#L224-L281)
- Our actual workflow runs FEMM 4.2 x64, 22 Oct 2023 build, under Wine 8 and Xvfb. Python generates cases and comparison tables using the standard library. Lua solves a periodic planar multilayer model with nonlinear B-H points, complex sources, weighted-stress-tensor forces, resistive losses, and incremental permeability from a previous nonlinear solution. [Local harness README](../../scripts/femm/README.md#harness), [recorded runs](../../scripts/femm/RESULTS.md#setup)
- Existing reference evidence includes mesh refinement, a wire-field analytical smoke test, nonlinear plate comparisons, bias-dependent incremental inductance, and harmonic traveling-wave drag with `loss/(F v)` checks. The thick near-knee plates fail the analytical model, while 2D drag agrees within 2.1%. The real finite-depth 3D drag and array-end eddy currents remain unchecked. These are local project results, not independent experimental validation. [Smoke test](../../scripts/femm/README.md#smoke-test), [results and limits](../../scripts/femm/RESULTS.md#saturation-and-eddy-currents-2026-10-18)

### Inferences
- Integrating sim-femm would mean writing a second model/backend adapter and adopting SIM runtime types. It would not reuse the existing generated FEMM Lua as a drop-in backend. Its own Rust solve path establishes that it neither embeds nor merely automates FEMM. [Solve implementation](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-solve/src/steady.rs#L52-L126)
- Removing Wine is attractive, but this implementation would remove reference physics needed by the current workflow. Retain FEMM as the 2D benchmark and use a separately validated 3D solver for finite magnet depth and ends. [Harmonic rejection](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-physics/src/implementation.rs#L170-L200), [local unchecked effects](../../scripts/femm/RESULTS.md#discussion)

### Gaps
- No installation, compilation, or numerical test was performed, as requested. Registry dependency metadata was checked, but published crate source was not compared byte-for-byte with the inspected Git revision.

## Which magnetic capabilities are actually implemented?

### Takeaway
The implementation does not meet the saturation, complex eddy-current, drag, or incremental-inductance requirements. Several named quantities exist as APIs but their formulas are not physical electromagnetic postprocessing. A convergence certificate here is not evidence that the intended magnetic PDE was solved.

### Cited Findings
- **Nonlinear B-H is not a working arbitrary material curve in the steady solve.** `Material` exposes `nu_of_b2`, but the PTC element residual ignores that expression and hardcodes `nu = 1/mu_r + 0.02*B²`. More seriously, the solve assembles once and sends PTC `linear_residual(K, offset, u)` with a constant cloned Jacobian. Assembly evaluates the local residual and derivative at zero nodal state. The cubic contribution therefore disappears from that assembled Jacobian, and the PTC front does not override the trait's default zero source term. These are directly observed source facts. [Material field](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-material/src/lib.rs#L48-L66), [PTC solve and front](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-solve/src/steady.rs#L128-L301), [zero-state assembly](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-assembly/src/implementation.rs#L249-L263), [default source](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-assembly/src/implementation.rs#L140-L145)
- **Complex AC eddy currents are explicitly unsupported.** `MagneticsHarmonicFront::validate_coeff` returns `UnsupportedPhysics` at every nonzero frequency because the real-valued assembly lacks `j*omega*sigma`. At zero frequency it reduces to the linear magnetostatic reluctivity. Unit tests assert these rejections. The README's harmonic language must not be read as operational AC support. [Implementation and tests](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-physics/src/implementation.rs)
- **Dimensionality is 2D.** `FemMesh2` holds `[x,y]` nodes and P1 triangular elements. Planar and axisymmetric formulations are exposed; axisymmetric integration uses a centroid `2*pi*r` weight. This is not a 3D vector-field/tetrahedral solver, and the presence of that weight is not proof of a correct axisymmetric magnetic-vector-potential formulation. [Mesh](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-mesh/src/implementation.rs#L79-L98), [element geometry](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-space/src/lib.rs#L113-L129)
- **Meshing is a basic fan, not a production multiregion mesher.** The default mesh connects node 0 to successive nodes and assigns every triangle the first block label. It does not use `max_area` or `min_angle_deg` in its triangulation routine. The public steady solve hardcodes this mesher. Boundary enums include periodic, Neumann, and Robin, but validation rejects every boundary kind except Dirichlet. [Triangulation](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-mesh/src/implementation.rs#L229-L292), [boundary validation](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-mesh/src/validation.rs#L75-L84), [steady entry](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-solve/src/steady.rs#L52-L63)
- **Magnetic excitation needs further physical work.** The linear front uses `1/mu_r` without an explicit vacuum-permeability factor. Assembly's coil source is `turns*current`, not that quantity divided by region cross-section. `remanence` exists in the material descriptor, but the inspected magnetic front and assembly source calculation do not turn it into a permanent-magnet excitation. [Linear front](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-physics/src/implementation.rs#L130-L157), [source calculation](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-assembly/src/implementation.rs#L284-L350)
- **Energy, force, and loss names do not establish physical outputs.** `energy` sums `0.5*element_measure*mean(u)^2`, not magnetic field energy. `ForceY` sums `-0.5*element_measure*(du/dy)^2` over a region; torque multiplies that by a centroid lever arm. `JouleLoss` integrates `|grad u|²` without conductivity or frequency. Planar element measure does not apply model depth in these routines. None is the weighted Maxwell stress or complex current loss used by our reference workflow. [Exact formulas](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-post/src/quantity.rs#L191-L200), [dispatch](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-post/src/quantity.rs#L243-L276), [measure and integrals](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-post/src/quantity.rs#L311-L380)
- **Inductance is not incremental inductance.** The implementation returns `L=2W/I²` and linkage `2W/I`, using the energy above. There is no bias-linearized differential-permeability solve in this quantity dispatch. Sensitivity infrastructure distinguishes adjoint and finite-difference paths, but its nonlinear parameter Jacobian also runs plus/minus steady solves; differentiation does not repair the physical model. [Inductance dispatch](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-post/src/quantity.rs#L261-L270), [sensitivity implementation](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-sensitiv/src/nonlinear_adjoint.rs#L87-L132)

### Inferences
- The advertised nonlinear PTC path is effectively a constant assembled linear problem, not a field-updated B-H saturation solve. It cannot fix normal-face saturation in thick near-knee plates. This conclusion follows algebraically from zero-state AD assembly and the constant residual callback, rather than from a numerical reproduction. [PTC callback](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-solve/src/steady.rs#L136-L152), [assembly](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-assembly/src/implementation.rs#L249-L263)
- Nonzero-frequency rejection alone disqualifies the current code for traveling-wave eddy drag and our 100 kHz impedance checks. The ODE/DAE adapters described in the README do not demonstrate a moving-conductor magnetic PDE, motional `v cross B` term, sliding interface, or finite-array end-current model. A 2D library cannot settle the unverified real 3D drag. [Harmonic gate](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-physics/src/implementation.rs#L170-L200), [README integration scope](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/README.md)
- A convergence certificate can certify convergence of the implemented algebraic system without certifying electromagnetic correctness, material fidelity, mesh convergence, or experimental accuracy. That distinction is decisive here. [Certificate description](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/README.md), [actual steady implementation](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-solve/src/steady.rs)

### Gaps
- No demonstrated SI normalization contract or independently validated magnetic benchmark was found that rescues the apparent missing material factors and source normalization. Do not use these outputs quantitatively without such evidence.
- No verified hysteresis/core-loss model, nonlinear AC harmonic balance, or magnetic transient/motion implementation was established in the inspected sources.

## Is it maintainable, deployable, and legally suitable?

### Takeaway
It is a young, actively worked-on Rust ecosystem project with real tests and CI, but the inspected tests do not establish engineering-grade magnetic accuracy. MPL licensing is more practical for embedding than FEMM's distribution terms, but a complete transitive license audit remains unfinished. The physics defects already make adoption a no-go.

### Cited Findings
- GitHub records creation on 2026-07-01 and latest push on 2026-09-29, with zero stars and forks at inspection. The releases API returned an empty list. This does not imply crates are unpublished: crates.io exposes `sim-lib-femm-prelude 0.2.2` and its versioned dependencies. [Repository metadata](https://api.github.com/repos/sim-nest/sim-femm), [releases](https://api.github.com/repos/sim-nest/sim-femm/releases), [published dependency metadata](https://crates.io/api/v1/crates/sim-lib-femm-prelude/0.2.2/dependencies)
- CI runs on `ubuntu-latest` and invokes formatting, Clippy, workspace tests, and rustdoc. Generated-document checking is explicitly nonblocking due to the tooling's toolchain-pin constraint. Recent workflow runs report success, but that is not physical validation. [Workflow](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/.github/workflows/ci.yml), [runs API](https://api.github.com/repos/sim-nest/sim-femm/actions/runs?per_page=4)
- Tests cover stable fixture names, simple analytical helper formulas, solve/postprocess execution, certificates, rejection of unsupported harmonic/nonlinear fronts, and internal gradient comparisons. In particular, tests of `parallel_plate_capacitance`, `long_solenoid_b`, and `harmonic_joule_loss` test the helper formulas directly, not solved-field accuracy against those references. [Physics tests](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-physics/src/implementation.rs), [fixture tests](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-fixtures/src/tests.rs), [gradient tests](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-sensitiv/src/tests.rs)
- Toolchain is pinned to Rust 1.96.0 and crates use edition 2024. The public integration requires SIM kernel/numbers/cookbook crates; it is not a small standalone FEMM-compatible Rust binding. Assembly allocates a dense `n*n` matrix before converting to CSR. Registered solver providers exist, but a sparse provider does not remove that assembly allocation. [Toolchain](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/rust-toolchain.toml), [prelude dependencies](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-prelude/Cargo.toml), [assembly allocation](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-assembly/src/implementation.rs#L224-L281)
- sim-femm declares MPL-2.0. License sections 3.1 to 3.4 require covered source, including modifications, to remain available under MPL when distributed, executable recipients to be told how to obtain that source, and notices to be retained. Separate files in a larger application may use other terms. This is file-level source-sharing, not automatic whole-application GPL treatment. [License](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/LICENSE)
- Transitive obligations cannot be reduced to the top-level license. Verified published dependency metadata marks `sim-kernel 0.4.0`, `sim-cookbook 0.4.0`, `sim-cookbook-build 0.2.0`, and `sim-lib-numbers-prelude 0.5.0` as MPL-2.0. The numbers prelude unconditionally pulls in many numeric domains and tensor backends. The inspected bigint manifest uses `num-bigint`, not GMP/Rug; no basis was found to assert a GMP obligation merely because it supports big integers. [Kernel metadata](https://crates.io/api/v1/crates/sim-kernel/0.4.0), [cookbook metadata](https://crates.io/api/v1/crates/sim-cookbook/0.4.0), [build metadata](https://crates.io/api/v1/crates/sim-cookbook-build/0.2.0), [numbers metadata](https://crates.io/api/v1/crates/sim-lib-numbers-prelude/0.5.0), [prelude manifest](https://github.com/sim-nest/sim-numbers/blob/main/crates/sim-lib-numbers-prelude/Cargo.toml), [bigint manifest](https://github.com/sim-nest/sim-numbers/blob/main/crates/sim-lib-numbers-bigint/Cargo.toml)
- FEMM's own licensing is materially different: its published Aladdin Free Public License restricts paid commercial distribution, but explicitly does not restrict functional use. Triangle and Lua have separate terms; Triangle commercial-system distribution requires arrangement with its author. Running an externally obtained FEMM in an offline reference workflow is therefore different from bundling FEMM/Triangle into a sold application. sim-femm's inspected own fan mesher is not Triangle. [FEMM and bundled component licenses](https://www.femm.info/wiki/License), [sim-femm mesher](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-mesh/src/implementation.rs#L229-L292)

### Inferences
- Native/headless Linux deployment should avoid FEMM's Wine/Xvfb dependency because this code solves in-process and Linux CI exercises it. Windows, macOS, browser/WASM, desktop packaging, and reproducible offline builds are not thereby verified. The broad SIM dependency set and dense assembly also undermine the apparent simplicity of adding one umbrella crate. [CI](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/.github/workflows/ci.yml), [dependencies](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-prelude/Cargo.toml), [assembly](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-assembly/src/implementation.rs#L224-L281)
- Recommendation: do not integrate for production or replace FEMM for validation. Reconsider only after arbitrary measured B-H curves, field-updated nonlinear assembly, complex harmonic eddy currents, multiregion quality meshing, periodic boundaries, permanent magnets, correct force/energy/loss, and differential inductance are implemented and compared against the existing benchmark tables. Actual 3D drag still needs a 3D solver or experiment. This recommendation follows the verified implementation blockers above, not repository popularity. [Core blockers](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-solve/src/steady.rs), [AC rejection](https://github.com/sim-nest/sim-femm/blob/dcc1205664cb74fc77aab7d62ae650cd2c0ac759/crates/sim-lib-femm-physics/src/implementation.rs), [reference requirements](../../scripts/femm/RESULTS.md#discussion)

### Gaps
- Full transitive SPDX inventory, exact resolved feature/version graph, native build dependencies, and any non-MPL third-party obligations are not certified. The inspected repository tree has no committed Cargo.lock, and no dependency resolution/install was performed. Before any shipping decision, generate a locked dependency graph/SBOM and inspect every license and notice, including build tools and platform backends. Do not read this assessment as a clean-license certification.
- No independently reproduced FEMM comparison, recognized electromagnetic benchmark suite, physical motor validation, performance scaling study, or supported-platform matrix was established. Internal finite-difference agreement and a passing CI badge are insufficient substitutes.
